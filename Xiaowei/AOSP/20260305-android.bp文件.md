# bp文件介绍

bp文件是为了替换mk文件，与mk文件不同，bp文件不能做分支、循环等流程控制，它是纯粹的配置文件，bp文件记录着模块信息，**每一个模块以模块类型开始，后面跟着模块的属性**，以名值对（`name: value`）表示，每个模块都**必须**要有一个`name`属性。

# 常见的编译类型

## android_app

- app，就是编写一个apk（从源码编译）

## android_app_import

- 导入预编译的apk（客户只给二进制APK、不给源码时用）
- 不编译源码，只做签名、dex预优化、分区放置、权限处理，然后打进镜像
- 对应mk的`BUILD_PREBUILT`，是它的bp写法

## cc_binary

- 可执行文件

## cc_library_shared

- native动态库

## cc_library_static

- native静态库

## java_library

- java库

# 基本使用

如果要编写apk，必须先指定模块源码路径和编译后的模块名称

```makefile
android_app {
    // 编译后的模块名称
    name: "messaging",
    
    // 该模块指定的源码路径，相对于bp文件所在目录的路径
    srcs: ["src/**/*.java"]
}
```

> 这个`messaging`就是模块名称，当需要改了某个模块的代码时，看到有bp文件，可以看看这个模块名称，再使用单编模块命令即可单编模块

# android_app_import 详细使用

## 和 android_app 的区别

| 场景            | 模块类型             | 核心属性                  |
| :-------------- | :------------------- | :------------------------ |
| 有源码，编译APK | `android_app`        | `srcs`、`manifest`、`res` |
| 只有APK二进制   | `android_app_import` | `apk`                     |

`android_app` 要 `srcs`（Java/Kotlin源码）、`manifest`、`res`，编译时把源码编成dex、链接资源、再签名；
`android_app_import` 不编译任何东西，只是把现成APK做签名、dex预优化、按分区放置、处理权限，然后打进镜像。

## 使用场景

- 客户提供的Launcher、系统应用等预编译APK
- Google等只给二进制的GMS应用（仓库里 `vendor/partner_gms/apps/` 下全是 `android_app_import`）
- 自己的prebuilt应用

## 基本写法

```makefile
android_app_import {
    name: "KubiLauncher",
    apk: "KubiLauncher.apk",        // APK文件路径，相对于bp文件所在目录
    certificate: "platform",        // 重签成platform证书
    // 或 presigned: true           // 保持客户原签名，二选一
    privileged: true,               // 装到priv-app
    system_ext_specific: true,      // 装到system_ext分区
    platform_apis: true,            // 使用平台API（对应mk的LOCAL_PRIVATE_PLATFORM_APIS）
    dex_preopt: { enabled: true },  // dex预优化，和android_app一样
    overrides: [                    // 覆盖系统模块，系统模块不再安装
        "Launcher2", "Launcher3", "Home",
        "Launcher3QuickStep",
    ],
    enforce_uses_libs: false,       // 跳过uses-library校验，客户APK常声明了系统没有的库
}
```

## 常用属性

| 属性                    | 含义             | 说明                                                     |
| :---------------------- | :--------------- | :------------------------------------------------------- |
| `apk`                   | APK文件路径      | 核心属性，`android_app`没有                              |
| `certificate`           | 签名证书         | `"platform"`重签成平台证书，或指定其他key                |
| `presigned`             | 保持原签名       | `true`时不再重签，客户APK要求保留自己签名时用            |
| `privileged`            | 特权应用         | `true`装到priv-app                                       |
| `system_ext_specific`   | system_ext分区   | 装到system_ext，也有`product_specific`、`vendor: true`等 |
| `relative_install_path` | 分区内子目录     | 如GMS的 `GmsCore/m/independent`                          |
| `arch`                  | 按架构选APK      | `arch: { arm64: { apk: "xxx_arm64.apk" } }`              |
| `platform_apis`         | 使用平台API      | 对应mk的`LOCAL_PRIVATE_PLATFORM_APIS`                    |
| `dex_preopt`            | dex预优化        | 和`android_app`一样                                      |
| `overrides`             | 覆盖其他模块     | 同名场景下系统模块不再安装，如覆盖Launcher3QuickStep     |
| `enforce_uses_libs`     | uses-library校验 | `false`跳过校验，客户APK常声明了系统没有的库             |
| `required`              | 依赖的其他模块   | 如权限白名单模块                                         |

## 注意点

- 客户APK若包名不是系统白名单里的包名（如不是`com.android.launcher3`），`privileged: true`需要配一份`privapp-permissions-<包名>.xml`放进`/etc/permissions`，否则开机权限校验会报错
- 签名方式和客户确认：要保留客户签名用`presigned: true`；要平台权限用`certificate: "platform"`重签（注意部分APK有签名校验，重签后可能跑不了）
- 老工程还在用mk写法`BUILD_PREBUILT`（如`LOCAL_OVERRIDES_PACKAGES`覆盖系统模块），新代码用`android_app_import`

# 许可证声明

每个 Android.bp 文件应该包含许可证声明：

```makefile
package {
    default_applicable_licenses: ["Android-Apache-2.0"],
}
```

> 从Android 10 开始强制要求，可以继承父目录的声明

# 常用属性

```makefile
android_app {
    name: "MyApp",
    srcs: ["src/**/*.java"],
    resource_dirs: ["res"],           // 资源目录
    manifest: "AndroidManifest.xml",  // Manifest 文件路径
    deps: [                           // 依赖的其他模块
        "androidx.appcompat_appcompat",
    ],
    static_libs: ["mylib"],           // 静态链接库
    sdk_version: "current",           // SDK 版本
    platform_apis: true,              // 使用平台 API
}
```

# filegroup模块

用于**将一组文件打包成一个逻辑名称**，方便其他模块引用。它本身不产生编译输出，只是一个"文件集合"的别名。

## 作用说明

`filegroup` 的核心作用是：

1. **简化依赖声明**：多个模块需要相同的一组文件时，只需引用一个 filegroup
2. **路径复用**：避免重复写长长的文件路径列表
3. **条件编译**：可以根据不同配置包含不同文件

```makefile
filegroup {
    name: "launcher-src",           // 文件集合的名称
    srcs: [                          // 包含的文件列表
        "src/**/*.java",             // 递归所有 Java 文件
        "src/**/*.kt",               // 递归所有 Kotlin 文件
        "JzhkLauncher3/src/**/*.java", // 另一个目录的 Java 文件
    ],
}
```

## 如何使用

其他模块可以通过 `srcs` 属性引用这个 filegroup：

```javascript
// 方式1：直接作为 srcs（使用 : 前缀）
android_app {
    name: "Launcher3",
    srcs: [":launcher-src"],  // 引用上面的 filegroup
    // 还可以添加额外文件
    srcs: [
        ":launcher-src",
        "src/debug/**/*.java",
    ],
}

// 方式2：与 java_defaults 配合
java_defaults {
    name: "launcher-defaults",
    srcs: [":launcher-src"],
}

android_app {
    name: "QuickStep",
    defaults: ["launcher-defaults"],  // 间接获得这些源文件
}
```

## 引用语法说明

| 写法                   | 含义                                                     |
| :--------------------- | :------------------------------------------------------- |
| `":模块名"`            | 引用**当前目录**的模块（必须在同一个 Android.bp 文件中） |
| `"//路径:模块名"`      | 引用**其他目录**的模块                                   |
| `"相对路径/文件.java"` | 直接指定源文件                                           |
