# 编译单元与编译命令判断

版本：V1.1，2026-08-13
适用平台：展讯 17 系 split build（SYS/VND/KERNEL 三棵树），Android 17
配套文档：`doc/预装APK的so库处理原理.md`（预装场景），`doc_编译脚本使用说明.md`（mk 脚本用法）

## 0 背景

改了代码后，怎么知道该编哪个组件、哪个模块、用哪个命令？本文回答两个问题：

1. 判断「改的文件属于哪个编译单元」的朴素方法——不依赖 mk 脚本（lsys/lothers 等快捷指令）
2. 没有 mk 脚本时，等效的编译命令怎么写

mk 脚本的本质：封装了 lunch 环境（产品名、release、变体）和编译入口，环境变量全部可以从 out 目录的 dumpvars.txt 拿到，编译入口是 soong_ui.bash 直调。脚本没了，这两样东西还在。

## 1 编译单元总览

展讯 split build 把整个 Android 分成多个编译单元，各自独立的 out 目录、独立的产品配置：

| 树     | 编译单元       | out 目录                                    | mk 快捷指令                | 主要放什么                     |
| ------ | -------------- | ------------------------------------------- | -------------------------- | ------------------------------ |
| SYS    | system         | `out_system`                                | `lsys` / `. mk msys`       | frameworks、普通 app、三方预装 |
| SYS    | android_others | `out_android_others`                        | `lothers` / `. mk mothers` | GMS 应用、个别工具（FotaApp）  |
| VND    | vendor         | `out_vendor`                                | `lvnd` / `. mk mvnd`       | vendor 侧模块                  |
| VND    | vnd_others     | `out_vnd_others`                            | `modm`                     | sepolicy、init.rc              |
| VND    | bsp            | `VND/bsp/out`                               | `mbsp`                     | bootloader、sensorhub          |
| KERNEL | kernel         | `KERNEL/out/uck_arm64_kernel6.18-<variant>` | `lkrn` / `. mk mkrn`       | 内核                           |

> **注意**：SYS 树不是全归 system 单元。实测 `out_android_others/.../obj/APPS/` 里有 Chrome64、YouTube、Drive、Messages、GoogleDialer、Velvet、WebViewGoogle64、FotaApp 等——GMS 应用走快速通道单独编译。三方预装（PopGames/SparkTube/BlockBlast）在 system 单元。

## 2 朴素判断流程（不依赖 mk 脚本）

### 2.1 第一步：文件在哪棵树

```
SYS/**    → system 或 android_others 单元
VND/**    → vendor / vnd_others / bsp 单元
KERNEL/** → kernel 单元
jzhk/**   → overlay，编译前先跑拷贝脚本（clone_drv.sh），再编对应组件
```

### 2.2 第二步：SYS 下模块归 system 还是 others

**方法一（最可靠，编过即可查）—— find 中间产物**：

```bash
find SYS/out_system SYS/out_android_others -maxdepth 7 -type d -name "<模块名>_intermediates"
```

实测：

```
BlockBlast_intermediates  → SYS/out_system/target/product/ussi_arm64/obj/APPS/   → system 单元
FotaApp_intermediates     → SYS/out_android_others/target/product/ussi_arm64/obj/APPS/ → others 单元
```

**方法二（没编过）—— 经验归类**：

- GMS 系应用（Chrome、YouTube、Google 全家桶）→ others 单元
- 普通 app、三方预装（third_preloadapp）→ system 单元
- 有例外（FotaApp 的 PRODUCT_PACKAGES 定义在 `module/product/app/main.mk`，中间产物却在 others），方法一才是最终裁判

**方法三 —— 看模块被哪个 product mk 收录**：

```bash
grep -rln "<模块名>" SYS/device/sprd/sys_mpool/module/
```

`module/product/app/main.mk` 收录的多数在 system；GMS 相关 mk（如 `module/product/app/gms_quickstart`）收录的在 others。

### 2.3 第三步：改的是模块源码还是 product 配置

| 改的文件                                         | 编译方式                             |
| ------------------------------------------------ | ------------------------------------ |
| 模块源码（app 的 Java/资源、Android.mk/bp、APK） | 可单编模块验证产物，进镜像需整编组件 |
| product 配置（`main.mk` 等 mk 文件）             | 必须整编对应组件，单编绕不过         |
| sepolicy（.te）                                  | 编 vnd_others 单元                   |
| jzhk overlay                                     | 先跑拷贝脚本再整编对应组件           |

### 2.4 整编后的逆推（有产物时）

整编完之后，从产物就能确定模块用哪个命令编：

**判定单元 —— find 实际中间产物**（最可靠）：

```bash
find SYS/out_system SYS/out_android_others -maxdepth 7 -type d -name "<模块名>_intermediates"
```

产物实际存在于哪个 out，模块就在哪个单元编译，编译命令随之确定（OUT_DIR + dumpvars 环境变量 + soong_ui 直调，见第 3 节）。

**看编译命令细节 —— ninja 文件**：

```bash
grep -n "BlockBlast" SYS/out_system/build-ussi_arm64_full_64only.ninja
```

ninja 文件里存有该模块每一步处理命令（拷贝、manifest_check 校验、签名、zipalign 等）。**注意**：system 和 others 的 ninja 文件都含全部模块规则（soong 生成完整蓝图），ninja 只能参考命令内容，不能判断单元归属——归属以实际产物为准。

### 2.5 干净代码时的预判（无产物时）

**system 与 android_others 的模块归属在源码里没有显式声明，干净代码时无法 100% 静态判断。** 机制依据：

- `lothers` 与 `lsys` 只差一个 OUT_DIR，lunch 是同一个 target（mk 脚本实测）
- 两个单元的 ninja 文件都包含所有模块的构建规则（BlockBlast 在两个 ninja 里都有完整规则）
- PRODUCT_PACKAGES 收录位置不是铁律（FotaApp 定义在 app/main.mk，产物却在 out_android_others）
- 归属由 split_build 工具（`SYS/vendor/sprd/release/split_build/`）编译时按 `--components android_others` 分解，模块清单不存在显式配置文件里（sys_config.yml 只定义组件属性）

实用预判组合：

| 手段                                                  | 有效性                         |
| ----------------------------------------------------- | ------------------------------ |
| 历史产物：上次整编后该模块 intermediates 在哪个 out   | 最可靠，编过一次就固化认知     |
| 经验归类：GMS 系 → others；三方预装/普通 app → system | 大部分对，有 FotaApp 类例外    |
| 模块名 + 命令模板：LOCAL_MODULE/name + 第 3 节命令    | 编译命令本身可以干净代码时确定 |

落地做法：新模块首次内置按经验选单元，整编后 `find` 确认一次产物落点，之后该模块的单元归属就定了。

## 3 不依赖 mk 脚本的编译命令

### 3.1 环境变量从哪来：dumpvars.txt

每个 out 目录都有 `dumpvars.txt`，记录了该编译单元的完整环境（实测内容）：

```
TARGET_PRODUCT=ussi_arm64_full_64only
TARGET_BUILD_VARIANT=userdebug
TARGET_BUILD_VERSION=gms
UNISOC_TARGET_RELEASE=unisoc_release
TARGET_PRODUCT_OUT_ROOT=out_system/target/product
```

17 系三段式 lunch 的 release 段（TARGET_RELEASE）与 UNISOC_TARGET_RELEASE 同值：`unisoc_release`。

### 3.2 17 系单编模块（绕过 lunch 直调 soong_ui）

```bash
cd SYS && export OUT_DIR=out_system TARGET_PRODUCT=ussi_arm64_full_64only \
    TARGET_RELEASE=unisoc_release TARGET_BUILD_VARIANT=userdebug \
    TARGET_BUILD_VERSION=gms UNISOC_TARGET_RELEASE=unisoc_release && \
build/soong/soong_ui.bash --make-mode <模块名> -j34
```

不同单元只换 OUT_DIR（和对应产品名）：

| 单元           | OUT_DIR                                   | TARGET_PRODUCT         |
| -------------- | ----------------------------------------- | ---------------------- |
| system         | out_system                                | ussi_arm64_full_64only |
| android_others | out_android_others                        | ussi_arm64_full_64only |
| vendor         | out_vendor                                | ugvi_arm64_full_64only |
| vnd_others     | out_vnd_others                            | ums9230_full_64only    |
| kernel         | KERNEL/out/uck_arm64_kernel6.18-<variant> | uck_arm64_kernel6.18   |

> **说明**：模块名从 Android.mk 的 LOCAL_MODULE / Android.bp 的 name 拿。单编只出模块产物，不进镜像。

### 3.3 16 系传统方式（source + lunch + mmm）

```bash
cd SYS && unset -f grep && export OUT_DIR=out_system \
    && source build/envsetup.sh && lunch ussi_arm64_full_64only-unisoc_release-userdebug-gms \
    && mmm <模块路径>:<模块名>
```

> **注意**：source envsetup.sh 前必须 `unset -f grep`，否则 lunch 会报误导性的 product 找不到（Bash 工具的 grep 是 ugrep 包装，见 `doc_编译脚本使用说明.md`）。

### 3.4 整编组件（无 mk 脚本时）

```bash
# system 单元整编
cd SYS && export OUT_DIR=out_system TARGET_PRODUCT=ussi_arm64_full_64only \
    TARGET_RELEASE=unisoc_release TARGET_BUILD_VARIANT=userdebug \
    TARGET_BUILD_VERSION=gms UNISOC_TARGET_RELEASE=unisoc_release && \
build/soong/soong_ui.bash --make-mode -j34
```

> **注意**：mk 脚本的整编命令（msys 等）除了编译还包含两步附加动作：overlay 拷贝（clone_drv.sh）和 merge 出包（PAC）。朴素写法只覆盖编译本身，overlay 改动要手动先跑拷贝脚本，出包要手动跑 merge——这两步没有脚本时容易漏。

### 3.5 验证编对了

```
1. 产物路径存在：
   ls SYS/out_system/target/product/ussi_arm64/system/app/<模块>/
2. 时间戳：产物 mtime 必须晚于源文件修改时间
   stat -c '%y' <源文件> <产物>
3. 内容正确：APK 大小/签名/so 目录（unzip -v、apksigner verify）
4. 设备上确认刷的是这个包：APK md5 对比设备与 out
```

## 4 mk 快捷指令与朴素命令对照

| 快捷指令            | 做的事                     | 朴素等效                           |
| ------------------- | -------------------------- | ---------------------------------- |
| `lsys`              | 进 SYS + lunch system 单元 | 3.2 的 export 环境                 |
| `lothers`           | 进 SYS + lunch others 单元 | 同上，OUT_DIR=out_android_others   |
| `lvnd` / `lkrn`     | 进 VND/KERNEL + lunch      | 同上，换 OUT_DIR 和 TARGET_PRODUCT |
| `. mk ms <模块>`    | 单编模块                   | `soong_ui.bash --make-mode <模块>` |
| `. mk msys`         | system 整编 + 出包         | 3.4 + 手动 overlay/merge           |
| `mstatus` / `mdiff` | overlay 工具               | 无朴素替代，git 自行分辨           |

## 5 快速决策表

```
改了 X → 想编什么？
├─ 文件在哪棵树 → 组件（第 2.1 节）
├─ SYS 下 → find 中间产物定位 system/others（第 2.2 节）
├─ 只是想验证模块 → 单编：soong_ui --make-mode <模块名>
├─ 模块要进刷机包 → 整编对应组件
├─ 改了 main.mk 等配置 → 必须整编
├─ 改了 sepolicy → vnd_others 单元
└─ 最终出包 → 整编 + merge / PAC
```

## 6 修改没生效时的验证（改动进没进产物）

编译后行为没变化，先别改代码，按顺序验证"改动到底有没有进产物"，把链路逐层切断。

### 6.1 第一层：内容验证（改动在不在产物里）

按改动类型查产物内容：

| 改动类型                   | 验证方法                                                     |
| -------------------------- | ------------------------------------------------------------ |
| APK / so / 文件拷贝        | `md5sum <源文件> <out产物>`，必须一致（或按预期不同）        |
| jar 里的 class             | `unzip -p <jar> <Class>.class \| strings \| grep <方法名或特征串>`，count=0 即陈旧 |
| Java 源码                  | 上一条基础上再用 `javap -c <class>` 看方法字节码             |
| 配置/属性（build.prop 等） | `grep <新值> out_*/target/product/<产品>/*/build.prop`       |
| 资源                       | `aapt2 dump badging <apk>` 查版本/资源变化                   |

### 6.2 第二层：mtime 验证（有没有重新编译）

```bash
stat -c '%y' <源文件> <out产物>
```

产物 mtime 必须晚于源文件。产物比源旧 = 编译根本没跑这个模块。

> **注意**：双树同步（rsync -a）保留源文件旧 mtime，同步后源 mtime 可能比产物早，soong 认为没变不重编，改动静默消失——已中招的判定就是 6.1 的 strings 方法，修法是 touch 源文件或删对应 `.intermediates` 目录。

### 6.3 第三层：设备验证（刷的是不是这份产物）

```bash
adb -s <serial> shell md5sum /system/app/<模块>/<模块>.apk
md5sum SYS/out_system/target/product/ussi_arm64/system/app/<模块>/<模块>.apk
```

哈希相同即设备跑的就是 out 里这份。**判断设备 build 用 md5，不要用 ro.build.date**（构建脚本按天钉死日期）。

### 6.4 第四层：链路排查（为什么没编进去）

按概率排查，前三条是实际踩坑高发区：

1. **编错单元**：find 中间产物确认模块在哪个 out（第 2.2 节），改的是 system 模块却只编了 others
2. **编了没进镜像**：单编只出模块产物，镜像里是整编/merge 的旧货——整编组件或 merge 后再验证
3. **overlay 覆盖**：改了基线代码但 jzhk overlay 有同名副本，编译时被覆盖（先搜 overlay 副本）
4. **RRO 覆盖**（资源类）：改了框架资源但被运行时 overlay 覆盖，设备上 `cmd overlay lookup` 查实际生效值
5. **增量编译缓存**：ninja 没检测到变化——强制重编该模块（删 `_intermediates` 目录或 touch 源文件）
6. **产物时间戳异常**：merge/PAC 阶段用的是旧产物——重跑 merge 或 clean 对应 out

### 6.5 一句话流程

```
内容验证（改动在产物？）→ mtime（重新编了吗？）→ 设备 md5（刷对了吗？）
→ 都不是 → 链路排查（单元/镜像/overlay/RRO/缓存）
```
